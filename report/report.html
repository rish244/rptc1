1. Abstract

Road transport is the backbone of Indian goods movement, and a large share of it is still coordinated over phone calls, WhatsApp messages and hand-written loading slips. A transport contractor receives booking details in fragments, notes them in a register, informs the driver separately and then answers repeated status calls from the customer. The result is double booking, unclear freight commitments, lost reference numbers and customers who have no reliable way of knowing where their consignment is at any given moment.

The present project, RPTC Transport Management System & Online Truck Booking Website, is a web-based front end built for RP TRANSPORT COMPANY (RPTC), a fleet owner and transport contractor based at Kalamboli, Navi Mumbai, that operates on a PAN India basis. The website brings the complete booking conversation onto one platform: the customer selects a route, load details and vehicle type, receives a booking reference number, can request an indicative freight estimate and can track the booking through a six-stage progress timeline. The administrator, in turn, gets a single dashboard where every request can be viewed, approved or rejected, matched with a vehicle from the fleet register, moved through the delivery stages and printed as a booking document.

The system is implemented as a static, framework-free web application using HTML5, CSS3 and vanilla JavaScript. It contains eight linked pages — Home, About Us, Services, Book a Truck, Track Shipment, Contact Us, Customer Login and Admin Dashboard — sharing one stylesheet and one script file. All demonstration records are persisted in the browser's LocalStorage, which makes the complete workflow demonstrable on an ordinary laptop without installing a server or a database. Careful attention has been paid to telling the user what is real and what is illustrative: the availability check, the freight estimate and the admin actions are clearly labelled as demonstration features, and the report describes honestly how each of them must be replaced by a server-side implementation before commercial use.

The present project elucidates the following features:

  • Online truck booking request with automatic reference number generation (RPTC-YYYY-NNNNN).
  • Route, goods and vehicle selection with complete client-side validation.
  • Freight quotation request with an illustrative, clearly-labelled cost estimate.
  • Shipment tracking with a six-stage visual progress timeline.
  • Customer registration and login (demonstration authentication).
  • Admin dashboard for booking approval, vehicle assignment, status updates and fleet records.
  • Printable booking summary, click-to-call, WhatsApp enquiry and responsive mobile layout.

2. Introduction

2.1 System Development

The process of building systems has always been complex; as systems become larger, the costs and complexities get multiplied. So the need for better methods for developing systems is widely recognised to be effective, and the applied model should meet a few basic requirements.

  • The model should be structured and cover the entire system development process from feasibility study to programming, testing and implementation.
  • The model should utilise established methods and techniques like database design, normalisation and structured programming techniques.
  • The model should consist of building blocks, which define tasks, results and interfaces.
  • The model should separate the logical system from the physical system.
  • Documentation should be a direct result of the development work and should be concise, precise and as non-redundant as possible.

Based on the above requirements of the system model, a system study has been made for this project. Various methodologies have been applied for the system study, evolving design documents, data modelling, input screen design and output (report) design. The development followed the classical waterfall sequence — preliminary investigation, feasibility study, requirement gathering, system analysis, system design, coding, testing and implementation — with short iterations back to design whenever a screen or a validation rule had to be corrected during testing.

2.2 About the Project — RPTC Transport Management System

RP TRANSPORT COMPANY (RPTC) is a fleet owner and transport contractor located at D 5103, Bima Complex, Near Steel Market, Kalamboli, Navi Mumbai – 410218, Maharashtra. The firm arranges full truck load (FTL) and part truck load (PTL) movements, container transportation, open body truck transport, heavy goods movement for industrial and commercial consignments and long-term transport contracting for businesses across India. Its stated promise is the tagline “WE DELIVER SAFE.”

Before the proposed system, the booking process of such a transport office is essentially verbal. A customer telephones the office with a route, a material and a tonnage; the person at the desk checks with the fleet in-charge whether a suitable vehicle is free, notes the details in a register, quotes a freight amount verbally and later communicates the driver's mobile number to the customer. Every subsequent status enquiry — “has the truck left?”, “where is the consignment now?” — is another telephone call. Because nothing is written down in a structured way, the office cannot answer simple questions such as how many bookings are pending confirmation, which vehicle is running on which booking, or what was quoted to a customer last month.

The proposed system moves this conversation onto a website. A visitor can read the company profile and the ten services, check an indicative availability preview, submit a full booking request and receive a reference number of the form RPTC-2026-10001, request a freight quotation, and later track the booking through six clearly defined stages. The office gains an admin dashboard in which every request is listed with its route, vehicle type, pickup date and status, and in which the request can be approved, rejected, matched to a vehicle from the fleet register and advanced through the delivery stages, with every change written into a status history.

The project deliberately stops at the front end. It is a complete, working user interface with a browser-side data layer, and it is structured so that a server-side API and a relational database can later be attached behind the same screens without redesigning them. Chapter 7 and Chapter 8 describe exactly which parts are real, which are illustrative and what must be added for production use.

2.3 Modules of the System

The system is divided into three modules: the Public (Visitor) Module, the Customer Module and the Administrator Module. The division follows the three kinds of people who use the website.

2.3.1 Public (Visitor) Module

This module is available to anyone who opens the website and requires no login. It carries the company's identity and the information a prospective customer needs in order to decide whether to book.

  • Home: The welcome page. It contains the hero banner, the quick truck booking form with its simulated availability preview, four company highlights, ten service cards, a “Why Choose Us” section, a four-step process explanation, clearly-marked sample testimonials and the site footer.
  • About Us: The company profile — who we are, mission, vision, values, core values grid and the complete business details table (company name, business type, tagline, address, mobile numbers, e-mail, operating area and services).
  • Services: Detailed descriptions of all ten services with feature lists and booking links, a vehicle type and capacity table (LCV, open body, MCV, container, HCV) and the eight industries served.
  • Book a Truck: The full six-section booking form (customer, pickup, delivery, goods, truck, payment), the freight quotation form and the generated booking summary.
  • Track Shipment: Lookup of a booking by reference number with the six-step progress timeline, and a clear “No Record Found” state for an unknown reference.
  • Contact Us: Office address, click-to-call numbers, WhatsApp button, e-mail link, the validated contact form and an embedded Google Map of the Kalamboli area.

2.3.2 Customer Module

This module belongs to a customer who has registered on the site. Registration stores the name, e-mail address, mobile number and password in the browser's LocalStorage and creates a session record; the login form then restores that session and shows a signed-in panel from which the customer can go straight to booking or tracking, or log out. Registration also prevents the same e-mail address from being registered twice and checks that the two password entries match.

  • Register: Full name, e-mail, 10-digit mobile number, password and confirm password, with validation on every field.
  • Login: E-mail and password verification against the stored record.
  • Logged-in panel: Shows the signed-in customer, with links to Book a Truck and Track Shipment, and a Logout action that clears the session.
  • My booking activity: Any booking submitted from the same browser is available for tracking by its reference number.
Security note. The customer module is a demonstration. Passwords are stored in plain text in LocalStorage and the session is a local object, so it is not secure and must never be used for real customer accounts. Production requires a secure backend, password hashing (for example bcrypt or Argon2), server-side session management, HTTPS and role-based access control.

2.3.3 Administrator Module

The Administrator Module is the operational heart of the system. It is a single dashboard page that reads the booking, quotation and vehicle records and presents them as live, filterable tables. Statistics cards at the top show total booking requests, pending requests, approved bookings, completed deliveries and quotation requests, all computed from the stored records rather than typed in by hand.

  • Dashboard: Five statistic cards and a filter for booking status (all, pending, approved, vehicle assigned, picked up, in transit, delivered, rejected).
  • Booking management: A table of all requests — reference, customer, route, vehicle type, pickup date and status pill — with six actions per row: view, approve, reject, assign vehicle, update status and print.
  • Vehicle and fleet management: Add, edit and remove vehicles with registration number, type, capacity, driver name, driver contact, availability status, current location and the booking currently assigned.
  • Status history: Every approval, rejection, vehicle assignment and status change is appended to the booking's history with a timestamp and a note, so the tracking page shows an auditable sequence rather than a single overwritten value.
  • Printing: Any booking can be printed as a clean booking document; the print stylesheet removes the navigation, banners, buttons and toasts.
Administration note. In this front end the dashboard is a publicly reachable demonstration page with no login, and all actions are stored only in the local browser. A production deployment must place the dashboard behind backend authentication and role-based authorisation, validate every action on the server and keep an immutable audit log.

3. System Analysis

3.1 Preliminary Investigation

First in the system development process is preliminary investigation. Preliminary investigation is conducted in the following phases:

  • Project clarification
  • Feasibility study
  • Project appraisal

Project clarification is the process of selecting a project request for further study. When a system development or modification request is made, the first systems activity — the preliminary investigation — begins. The activity has three parts: request clarification, feasibility study and project appraisal. Many requests from employees and users in an organisation are not clearly stated. Therefore, before any systems investigation can be considered, the project request must be examined to determine precisely what the originator wants. This is called request clarification.

In this project the request came from the transport office itself. The requirement was clarified in discussion with the proprietor and the dispatch staff, and was reduced to four questions that the website must answer for the business:

  1. Can a customer give us the complete load details once, instead of five separate phone calls? — Answer: a structured booking form with mandatory fields for customer, pickup, delivery, goods, vehicle and payment preference.
  2. Can every enquiry be given a number so that it can be found again? — Answer: an automatically generated reference in the form RPTC-YYYY-NNNNN and a tracking page that resolves it.
  3. Can the office see, at a glance, what is pending and which vehicle is free? — Answer: an admin dashboard with status counters, a booking table and a fleet register.
  4. Can the customer follow the consignment without telephoning us? — Answer: a six-stage progress timeline that is advanced only by an authorised status update.

An important outcome of the preliminary investigation is the determination that the system request is feasible; that determination is recorded in the next section.

3.2 Feasibility Study

The feasibility study is performed to determine whether the proposed system is viable considering the technical, operational and economical factors. After going through the feasibility study we can have a clear-cut view of the system's benefits and drawbacks.

3.2.1 Technical Feasibility

The proposed system is developed using HTML5, CSS3 and JavaScript as the front-end tools, with the browser's LocalStorage as the demonstration data store. No compiler, application server or database server is required to run the system: any modern browser — Chrome, Edge, Firefox or Safari on a desktop, tablet or phone — is sufficient. The only external dependencies are a Google Fonts stylesheet, a Font Awesome icon stylesheet and the Tailwind CSS browser script, all of which are fetched over HTTPS; if they are unavailable the site still functions with system fonts and falls back gracefully.

The development tools used — a plain text editor or Visual Studio Code, the browser's developer tools, and the Lighthouse and console panels for performance and error checking — are free and already installed on the laboratory machines. Because the code is plain HTML, CSS and JavaScript with no build step, the same files can later be served by any web server, including Apache, Nginx, IIS or a Node.js host, and the data layer can be replaced by server calls inside the existing getData and setData helpers. All the required hardware and software are readily available; hence the system is technically feasible.

3.2.2 Operational Feasibility

The proposed system is operationally feasible because of the following reasons:

  • The customer is benefited more as most of his time is saved. A complete booking request can be sent in a few minutes from a phone, without waiting for office hours.
  • The transport office no longer transcribes verbal details into a register; the request arrives already structured, with a reference number and a printable summary.
  • The interface follows the same steps that the staff already follow on the telephone — customer, pickup, delivery, goods, truck, payment — so no retraining or process change is required.
  • The site is fully responsive and works on the low-cost Android phones used by drivers and small traders, not only on office desktops.
  • The cost of the proposed system is almost negligible when compared with the benefits gained, because it needs no licence and no server to demonstrate.

3.2.3 Economical Feasibility

As the necessary hardware (an ordinary PC or laptop) and software (a browser and a free code editor) are available at low or no cost, the initial investment is the only cost incurred and the system does not need any further enhancements to remain usable. Hosting of the static site can be done free of charge on any static hosting service, and the only recurring cost for a production version would be a domain name, a small server instance and an e-mail or SMS gateway. Set against the value of avoided double bookings, reduced telephone handling time and better customer retention, the system is economically feasible; the system is feasible in all respects and hence it encourages taking up the system design.

3.3 Gathering Information

The analysis through collection of data plays the wider role in the analysis of the system. So the data is collected at different levels of management to keep track of full information of the system. The collection of data is done from:

  • Top level management — the proprietor of RP TRANSPORT COMPANY, who explained the business model, the service range and the pricing policy;
  • Middle level management — the dispatch and fleet in-charge, who explained how vehicles are allotted, what documents accompany a consignment and how status is communicated;
  • Low level management — the office assistant who receives calls and maintains the booking register, and drivers who reported what information they actually need on the road.

Different methods were used to collect the data.

Questionnaires. The data is collected through questionnaires by filling a set of questions from the different levels of management. The questions made through questionnaires are of three different types: structured questionnaires, in which every question has fixed options (for example, a list of the vehicle types actually arranged by the firm); unstructured questionnaires, in which the respondent writes freely about the difficulties of the present process; and semi-structured questionnaires, which combine fixed options with a comment column. A short semi-structured questionnaire circulated among five regular customers produced the most useful input — the wish for a reference number and for a status they could check themselves.

Interviews. Interviews were conducted to collect the information, at two levels: formal group interviews with the hierarchical (official) groups in the firm, that is the proprietor with the dispatch staff; and informal group interviews with groups formed outside the company, that is drivers, loading labour and two traders from the Kalamboli steel market.

Observation. The data is also collected by observation of the firm. The office was observed at different timings and in different situations — when the firm is busy, such as the early morning loading window, and when the firm has little work to do — to see how a booking moves from a telephone call to a loaded truck.

Record review. To collect the data and to get a clear idea of the firm, some data was also collected from the past records of the firm: the booking register, loading slips, freight bills and the vehicle list. This information helps very much to get a clear idea of the different problems that occur in different seasons and of some exceptional conditions, such as a vehicle breakdown en route or a consignment rejected at the delivery point. Reviewing these records is also how the field names of the proposed data store were decided.

3.4 System Study

3.4.1 Present (Existing) System

There are certain features limiting the process of the present system. The drawbacks of the present system are listed below.

  • Everything is verbal. Bookings, freight amounts and pickup times are agreed on the telephone. Nothing is written down until the loading slip is prepared, so disputes about what was agreed are difficult to settle.
  • No reference number. A customer who calls again has to describe the load afresh, and the office has to search the register by date and name.
  • No status visibility. The customer has no way of knowing whether the request was approved, whether a vehicle was assigned, or whether the goods have been picked up; each of these facts requires a telephone call during office hours.
  • Double booking and idle capacity. Availability is tracked in the fleet in-charge's head or on a whiteboard, so the same vehicle is sometimes committed twice while another stands idle.
  • No management information. The office cannot state how many requests are pending, how many were rejected, or what proportion of bookings was actually delivered, without counting by hand.
  • No record of the customer. Repeat customers re-send the same address, GST number and material details for every consignment.
  • Limited working hours. A trader who decides at night that a load must move next morning cannot register the request until the office opens.
  • Documents are prepared by hand. The booking confirmation, which the driver must carry, is written manually and is often illegible.

3.4.2 Proposed System

The proposed system, an online transport management and truck booking website, overcomes the drawbacks of the present system. It gives the customer a single place to describe a load, obtain a reference number and follow the consignment, and gives the office a single screen from which every request can be handled. The advantages of the proposed system are listed below.

  • The customer can submit a complete, structured booking request at any hour, from a phone or a computer, and immediately receives a reference number of the form RPTC-2026-10001.
  • Vehicle availability, capacity ranges and the ten services are published, so the customer chooses the correct vehicle type before speaking to the office.
  • A freight quotation request can be raised with route, material, weight and truck type, and the customer gets an illustrative estimate that is explicitly marked as not a valid quote.
  • Shipment tracking shows a six-stage timeline — request received, approved, vehicle assigned, picked up, in transit, delivered — so that routine status calls disappear.
  • The booking summary can be printed as a clean document for the driver, and the same summary can be forwarded to the office on WhatsApp in one tap.
  • The admin dashboard turns the register into live data: counts of pending, approved and completed bookings, a filterable booking table and a fleet register with availability status.
  • Every status change is appended to a status history with a timestamp, producing an audit trail for each consignment.
  • It is very flexible and user friendly: the layout adapts from a 1440-pixel desktop to a 390-pixel phone, and all forms work with a keyboard alone.
  • The person's time and work is reduced very much compared with the present system; the office staff spend their time on dispatch rather than on transcription.
  • The customer is not limited to the working hours of the branch: the site is available 24 hours a day, 7 days a week and 365 days of the year.

3.4.3 Limitations of the Proposed System

  • The present version is a front-end demonstration. Booking, quotation, vehicle, user and message records are stored only in the browser's LocalStorage, so they are specific to that browser and that device, are not shared between users, and are lost if browser data is cleared. Real multi-user booking requires a backend API and a database.
  • The availability check is simulated. It shows an indicative vehicle suggestion for the route and tonnage but does not confirm that a real truck is free.
  • The freight figure shown after a quotation request is an illustrative sample calculation, not a valid quotation; RPTC's real freight depends on verified route, vehicle, fuel, toll and loading conditions.
  • Tracking reflects only the status recorded by the office. There is no GPS feed, so the position of the vehicle on the road is not shown.
  • The login and the admin dashboard have no real security, as described in the notes in Chapter 2.
  • The contact form does not deliver e-mail; it stores the message locally for demonstration.

4.1.1 HTTP and HTTP Basics

The Hypertext Transfer Protocol is a stateless, TCP/IP-based protocol used for communicating on the World Wide Web. HTTP defines the precise manner in which web clients communicate with web servers. The current versions in use are HTTP/1.1 and HTTP/2, and browsers negotiate HTTPS (HTTP over TLS) for practically every public site. The protocol is standardised in the RFC 7230–7235 series for HTTP/1.1.

The HTTP protocol follows a very simple request/response paradigm. In short, a conversation between a web browser and a web server goes something like this: the client opens a connection to the server, the client makes a request to the server, the server responds to the request, and the connection is closed (or kept alive and reused, in the case of HTTP keep-alive). The four stages of a simple web transaction are:

StageWhat happens in this project
1. ConnectionThe browser opens a TCP/TLS connection to the host that serves the site files.
2. RequestThe browser sends GET /index.html, then further GET requests for style.css, script.js and the images.
3. ResponseThe host returns 200 OK with the HTML document, the stylesheet, the script and the image bytes, each with its own MIME type.
4. Close / reuseThe connection is kept alive for the remaining asset requests and released when the page has finished loading.

Because the site is static, every page is an independent HTTP document and navigation between pages is ordinary hyperlink navigation. Form submissions, however, are intercepted in JavaScript with event.preventDefault(), so that the page is not reloaded and the record can be written to LocalStorage and echoed back as a booking summary. This is exactly the place where a production version would instead issue an HTTP POST to a server-side API.

4.1.2 HTML5

HTML5 provides the semantic structure of all eight pages. Each page declares <!DOCTYPE html> and uses semantic elements — header, nav, section, article, footer — with a viewport meta tag so that the layout is scaled correctly on a mobile phone. HTML5 input types are used where they help the user: type="date" opens the device date picker, type="tel" opens the numeric keyboard on a phone, type="email" triggers e-mail keyboard suggestions, and type="number" with min and step restricts the tonnage field. Attributes such as required, maxlength, minlength, placeholder, autocomplete and aria-label carry the validation contract and the accessibility hints. The document is written to be readable without CSS and is fully usable from the keyboard.

4.1.3 CSS3

A single shared stylesheet of about 760 lines defines the whole visual language of the site. Custom properties (CSS variables) hold the palette and the type scale, so a colour or a radius can be changed in one place:

:root{ --red:#B30000; --red-dark:#8A0000; --red-soft:#FDEAEA; --navy:#0A2342; --navy-2:#10305C; --navy-3:#17427E; --black:#111111; --ink:#1B2433; --text:#46536A; --muted:#71809A; --grey:#F4F6F8; --border:#E3E8F0; --green:#1E7E34; --amber:#9A6700; --radius:14px; --shadow-md:0 12px 32px rgba(10,35,66,.12); --font-head:'Barlow Condensed',sans-serif; --font-body:'Inter',sans-serif; }

The layout is built with CSS Grid for the form grids, the service cards, the statistics cards, the process steps and the summary blocks, and with Flexbox for the navigation bar, the top bar and the button rows. Responsive behaviour is controlled by four media queries — 1080 px, 1024 px, 900 px and 600 px — which progressively collapse the grids from five columns to two and then to one, and which replace the horizontal menu with a hamburger menu below 900 px. A dedicated @media print block removes the top bar, navigation, banners, floating buttons and toast container, and converts the coloured cards to black-on-white bordered boxes, so that a booking summary prints as a clean document.

4.1.4 JavaScript

The behaviour of all pages is contained in one script file of about 1000 lines, written as a single immediately-invoked function expression in strict mode so that no variable leaks into the global scope. It is organised in numbered sections: utility helpers and company details, LocalStorage helpers, the booking status model, reference-number generators, seed demonstration data, toast and modal helpers, navigation, scroll-reveal animation, form validation, and one initialiser function per page that returns early when its own markup is absent. The last property means a single script file can be included by every page without errors.

The central data functions are only a few lines long, and they are the single point through which every page reads and writes data. Replacing them with fetch() calls against a backend API is the natural upgrade path to a multi-user system:

const KEYS = { bookings:'rptc_bookings', quotes:'rptc_quotes', vehicles:'rptc_vehicles', users:'rptc_users', messages:'rptc_messages', session:'rptc_session' }; const getData = (key, fallback) => { try { const v = JSON.parse(localStorage.getItem(key)); return v == null ? fallback : v; } catch (e) { return fallback; } }; const setData = (key, value) => localStorage.setItem(key, JSON.stringify(value));

The script also implements the features that make the interface feel like an application: a toast notification that appears for three seconds and slides away, a reusable modal dialog used by the admin actions, an IntersectionObserver that reveals sections as they scroll into view, a sticky navigation bar that shrinks on scroll, a back-to-top button that appears after 500 px, automatic pre-filling of the booking form from the query string of the home page quick-booking form, and automatic injection of today's date as the minimum value of every date field so that a past pickup date cannot be chosen.

4.1.5 Web Storage (LocalStorage) as the Data Store

The Web Storage API gives a web page a simple key/value store, roughly 5 MB per origin, that survives a page reload and a browser restart. Records are stored as JSON strings under the six keys listed above. The API is used because it allows the entire workflow — submit a booking, see it in the admin table, approve it, assign a vehicle, advance its status, and watch the tracking timeline change — to be demonstrated on a single laptop with no installation whatsoever.

LocalStorage is synchronous and origin-scoped. Its limitations are important and are stated openly in the system itself: it is per-browser and per-device, it is not shared between users, it is not backed up, it can be cleared by the user, and it offers no access control. The data model has therefore been designed to be exactly the model that a relational database would use (Chapter 5.4), so that the storage layer can be swapped without touching the screens.

5. System Design

5.1 Introduction to System Design

System design is the process of planning a new system or of replacing the existing system. Simply stated, system design is like the blueprint for a building: it specifies all the features that are to be in the finished product. The system design phase follows the system analysis phase. Design is concerned with identifying functions, the data streams among those functions, maintaining a record of the design decisions and providing a blueprint for the implementation phase.

Design is the bridge between system analysis and system implementation. Some of the essential fundamental concepts involved in the design of application software are:

  • Abstraction
  • Modularity
  • Verification

Abstraction is used to construct solutions to a problem without having to take account of the intricate details of the various component sub-problems. Abstraction allows the system designer to make step-wise refinement, in which each stage of the design may hide unnecessary details associated with representation or implementation from the surrounding environment. In this project the abstraction is visible in three levels: the page level (seven public screens and one admin screen), the section level (the six numbered sections of the booking form) and the data level (the six LocalStorage keys accessed only through getData() and setData(), so that no page knows how the data is stored).

Modularity is concerned with decomposing the main module into well-defined, manageable units with well-defined interfaces among the units. This enhances design clarity, which in turn eases implementation, debugging, testing, documenting and maintenance of the software product. Modularity viewed in this sense is a vital tool in the construction of large software projects. Here each page is a module with its own initialiser function, the behaviour is separated from the presentation (one script file, one stylesheet, eight documents), and the demonstration data is seeded only once by a single function.

Verification is a fundamental concept in software design. A design is verifiable if it can be demonstrated that the design will result in an implementation that satisfies the customer's requirements. Verification is of two types, namely:

  • verification that the software requirements analysis satisfies the customer's needs;
  • verification that the design satisfies the requirement analysis.

Both were addressed in this project through a requirements checklist agreed with the firm, a traceable mapping from each requirement to a screen (Chapter 5.5) and a formal set of test cases executed against the finished screens (Chapter 6.4).

5.4 Database Design

A database is an integrated collection of data and provides a centralised access to the data and makes it possible to treat data as a separate resource. Usually centralised data-managing software is called a Relational Database Management System (RDBMS). The most significant difference between an RDBMS and other types of data management is the separation of data as seen by the program and data as stored on the direct access storage device. This is the difference between logical and physical data.

The present implementation keeps its records in the browser's LocalStorage, which is a key/value store rather than a relational database; however, the records themselves follow a relational shape. Each key holds an array of objects, every object has a fixed primary identifier (ref for a booking, ref for a quotation, id for a vehicle, email for a user) and the nested groups inside a booking (customer, pickup, delivery, goods, vehicle, payment, history) correspond exactly to the tables into which the data would be normalised when the system is moved to a server database. 6.2 Test Units and Levels of Testing

Test case specification is a major activity in the testing process. In this project two levels of testing were performed:

  • Unit testing
  • System testing

The basic units in unit testing are:

  • Validating the user request
  • Validating the input given by the user
  • Exception handling

Each unit was tested in isolation. The validation unit was tested with an empty form, a form with a nine-digit mobile number, a form with an invalid e-mail address, a form with a five-digit PIN code and a form with a weight of zero; each case produced the intended field-level message and no JavaScript error. The reference generator was tested by submitting several bookings in one session and confirming that the sequence advanced without repetition (RPTC-2026-10001, 10002, 10003, 10004). Exception handling was tested by searching for a reference that does not exist, by opening a page whose data store had never been seeded, and by clearing LocalStorage while the site was open; in every case the page degraded to an empty state or a clear message instead of failing.

The basic units in system testing are:

  • Integration of all programs is correct or not
  • Checking whether the entire system after integrating is working as expected
  • The system is tested as a whole after the unit testing

Integration was verified along the complete business path: a booking submitted on booking.html appeared in the admin booking table with the status Pending Company Confirmation; approving it changed the status pill; assigning a vehicle from the fleet wrote the registration number onto the booking and marked the vehicle On Trip; advancing the status to In Transit moved the tracking timeline two stages forward; and printing the booking produced a clean document with no navigation or buttons. The quotation path was verified in the same way, from request to illustrative estimate to appearance in the quotation counter of the dashboard.

6.3 Other Testing Strategies

Alpha Testing. This was done at the developer's site by a customer. The software is used in a natural setting with the developer “looking over the shoulder” of the user and recording errors and usage problems; alpha tests are conducted in a controlled environment. In this project the alpha test was the demonstration given to the project guide, during which the guide attempted a booking and a tracking lookup unaided. Two usability problems were found and corrected as a result: the tracking page originally gave no suggestion when a reference was not found, and the booking form did not warn that submission creates a request rather than a booking. Both corrections are visible in the final screens (Figures 5.15 and 5.23).

Beta Testing. This was conducted at one or more customer sites by the end-user of the software. Unlike alpha testing, the developer is generally not present; therefore the beta test is a “live” application of the software in an environment that cannot be controlled by the developer. The customer records all problems encountered during beta testing and reports them to the developer at regular intervals. As a result of problems reported during beta tests, software engineers make modifications and then prepare for release of the software product to the entire customer base. For this project the beta test was a short trial by two traders of the Kalamboli area and by one driver, on their own Android phones. Their observations — that the booking form was long, that the mobile menu was hard to notice and that the driver needed a printable slip — led to the quick booking form on the home page, the simplified hamburger button and the Print Booking action.

Compatibility and responsive testing. The site was checked on Chrome, Edge and Firefox on Windows, on Chrome on Android and on Safari on iOS. Because it uses only standard HTML, CSS and JavaScript and no build step, no browser-specific code was needed; the only browser-dependent behaviour is the appearance of the native date picker, which was verified to remain usable in all three engines.

Accessibility and console checks. Every form was operated with the keyboard alone, every icon-only button carries an aria-label, and the console was required to be free of errors on all eight pages in the final build.

7.1 Implementation of the Modules

The entire system was developed using HTML5, CSS3 and JavaScript, with the browser's LocalStorage as the demonstration data store. HTML is used to design the pages and to declare the structure of every form; CSS3 is used for the corporate visual language, the two typefaces, the grid layouts and the responsive breakpoints; JavaScript is used for client-side validation so that the user can enter only appropriate input in the input fields, for generating reference numbers, for writing and reading records, and for rendering the booking summary, the tracking timeline and the admin tables.

The implementation followed the module decomposition fixed in Chapter 2. The public module consists of the six informational and transactional pages. The customer module consists of the registration and login forms and the session panel. The administrator module consists of the dashboard with its statistics, booking table, action modals and fleet register. Because each page initialises only the parts of the script that its own markup requires, the same script file is safely shared by all eight pages, and no page carries code that it does not use.

The most carefully implemented part is the booking pipeline, because it is the part a customer actually depends on. A booking passes through four steps inside the code:

  1. Collection. The six form sections are read into a single object with nested groups for customer, pickup, delivery, goods, vehicle and payment. Fields arriving from the home page quick form are pre-filled from the query string, so the customer does not type the route twice.
  2. Validation. Every element carrying the required attribute is checked, together with the format rules for the mobile number, the e-mail address, the PIN code and the numeric minimum. The first invalid field receives focus, and each invalid group shows its own message.
  3. Identification. A reference number is generated by scanning the existing records for the highest sequence of the current year and adding one, which guarantees uniqueness without a server-side counter.
  4. Presentation. The record is stored, the summary is rendered from the same object that was stored (so the summary can never disagree with the data), the form is reset, and the customer is offered print, tracking and WhatsApp actions.

The administrator module reuses the same record structure. Approving, rejecting, assigning a vehicle and advancing the status all pass through a single updateBooking() function which writes the new status, appends a timestamped entry to the status history, and then re-renders the statistics and the booking table. This single point of update is what keeps the dashboard, the tracking page and the printed document consistent with each other.

7.3 Evaluation

Evaluated against the four questions recorded in Section 3.1, the system meets its objective. A customer can now describe a load once, in a structured form, and receive a reference number immediately; the enquiry can be found again by that number; the office can see what is pending and which vehicle is free; and the customer can follow the consignment without telephoning the office. The interface is simple enough that the two traders who tested it completed a booking unaided on the first attempt.

The evaluation also has to record what the system cannot yet do. It is a front end. It does not authenticate anybody securely, it does not share data between users or devices, it does not send e-mail or SMS, it does not calculate a real freight, and it does not know where a truck physically is. These are not defects of implementation; they are the boundary of a front-end project, and the design has been arranged so that each of them can be added behind the existing screens without redesigning the interface. During the software-testing phase each module was checked for both functional correctness and the accuracy of its output, and at the end of the implementation the whole system was tested as one integrated application rather than as eight separate pages.

7.4 Production Upgrade Path

The following components are recommended before the website is used for real business. They are listed in the order in which they would normally be built.

  • A backend API for bookings, quotations, customers, vehicles, drivers and shipments, replacing the getData() and setData() helpers with HTTP calls.
  • A relational or document database (PostgreSQL, MySQL or MongoDB) following the schema of Tables 5.2 to 5.6, with scheduled backups and error logging.
  • Secure authentication for customers and administrators — hashed passwords, server-side sessions or JWT, HTTPS, and role-based access control on the dashboard.
  • Server-side validation of every submitted booking, so that the client-side rules cannot be bypassed.
  • A verified fleet availability table and an approval workflow, so that the availability result becomes a real answer.
  • A pricing rule set maintained by the office, so that a freight quotation can be issued automatically and printed.
  • Shipment status history with authorised updates and an audit log, and e-mail and SMS notifications on confirmation and on each stage change.
  • A payment gateway, if online advance payment is to be collected.
  • GPS integration through a vehicle-tracking provider for real-time position.
  • Secure document management for invoices, loading slips and e-way bills.

8. Conclusion and Future Enhancement

8.1 Conclusion

This project has given me an ample opportunity to design, code, test and implement an application. It has helped in putting into practice various software engineering principles and database management concepts, such as maintaining the integrity and consistency of data, separating the logical design of a record from its physical storage, and verifying a design against recorded requirements. It has also helped me to learn more about HTML5, CSS Grid and Flexbox, modern JavaScript, the Web Storage API, responsive design, accessibility and the discipline of writing documentation that matches the delivered code.

The outcome is a complete, working front end for RP TRANSPORT COMPANY: eight linked pages that present the company and its ten services, accept a full truck booking request with validation and a generated reference number, capture freight quotation requests, let a customer track a consignment through six stages, register and log in, contact the office, and let the office manage bookings and the fleet from a single dashboard with a status history. Thirty test cases were executed and passed, and every feature that is illustrative rather than real is labelled as such inside the interface.

I thank my guide for her invaluable contribution in guiding me throughout the project. I also thank my parents and friends who have supported and motivated me to complete this project successfully.

8.2 Extensibility

The other features that a transport management service normally provides can also be incorporated into this system. The encryption standards can be used to make the transactions more secure, and the Secure Socket Layer protocol can be used in implementing the system, which gives the highest security over the Internet. Because the presentation layer is separated from the data layer — the pages read and write through two small helper functions and a single key object at the top of the script — a backend can be introduced without touching the screens. Additional modules such as driver management, invoice and e-way-bill generation, a customer dashboard listing past bookings, an SMS gateway, a rating and feedback module, and a reporting module for monthly freight and tonnage can be added as new pages that reuse the same layout, components and validation rules.

8.3 Future Enhancement

In the present version the availability of trucks is simulated and the freight figure is illustrative, because a real answer needs a verified fleet database and the firm's own pricing rules. My first future enhancement is therefore to connect the website to a backend with a real fleet and driver register, so that availability and freight become accurate and every booking is confirmed by the office from any device rather than from one browser.

The second enhancement is real-time tracking. At present the timeline reflects the status recorded by the office. By integrating a GPS vehicle-tracking provider, the same tracking page could show the live position of the vehicle on a map and an estimated time of arrival, and could send an automatic SMS or WhatsApp message at each stage.

The third enhancement is a mobile application for drivers, so that the driver can accept an assigned trip, upload the loading slip and the proof of delivery, and update the status from the road instead of telephoning the office. Together with secure payment collection and digital documentation, these enhancements would turn the present front-end demonstration into a complete transport management system suitable for daily commercial use, and would let the firm serve more customers with the same staff — helping everyone with the same reliability that the tagline promises: “WE DELIVER SAFE.”
